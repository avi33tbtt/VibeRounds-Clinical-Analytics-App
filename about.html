Why it exists

Hospitals and health systems now hold large amounts of patient data in FHIR, but getting a trustworthy answer from it is still slow, specialist work. Four problems come up again and again:

The problemWhat Vibe Rounds gives you
The answer depends on how you read the record. Ask "how many patients have diabetes?" of the notes, of the codes, or of the codes with dates, and you often get three different numbers. Most tools show you one, without saying so.Up to five answers side by side. Every analytic runs, where it makes sense, from the clinical notes (V1), the codes (V2), the codes plus reviewed enrichment codes (V3), the codes with dates (V4), and enriched codes with dates (V5) on the same patients. You can see how much a result depends on the method and where the data is weak, and a built-in comparison shows exactly what enrichment changed.
You do not know if the data is any good. Missing codes, local code systems, duplicates and impossible dates only surface after weeks of work, if at all.A data check up front. Coding coverage, unrecognised code systems and date problems are measured first, so you know what the data can support before you build on it. Analytics readiness goes one step further: it runs every analytic in each method once and tells you which ones this data can support, and why not for the rest.
Turning a clinical question into a study takes skill and time. You need to know the code sets, write cohort SQL, pick an analysis and decide what to look at next.A faster path from question to result. Type the question in plain English or ask for suggested studies, and the form is filled in for you. A query builder writes the cohort SQL from clinical concepts, including descendants in the SNOMED CT hierarchy.
General AI chat tools can invent numbers. A model that writes its own queries and quotes its own figures is hard to trust or to check in a clinical setting.An assistant that guides but does not calculate. The model reads results, flags what stands out, and proposes the next analysis from a fixed catalog. Every number comes from a tested analytic (or a query you reviewed), and you decide each step. The one exception to click-by-click is the optional AI researcher, which runs a number of rounds you set (below).

The value, in short: you get to a defensible first answer sooner, you know how much the method and the data quality matter, and you leave with something reusable, the SQL, instead of a one-off number. It does this on synthetic or de-identified data, with no need to convert your data to another model first.

What it does

You bring FHIR patient data, from your own files, the open HAPI FHIR test server or a built-in synthetic generator, and work through it in PostgreSQL: define a cohort, run a catalog of clinical analytics (prevalence, medication use, lab control, readmissions, care gaps, drug safety, data quality and more), and let the AI assistant read the results with you.

The assistant is analyst-led. After each run it reads every result so far, together with the choices you have already made. It summarizes where the analysis stands, flags what it noticed (important, unusual, caution, data quality), and proposes up to four next analytics with a short reason each. You run a suggestion, skip it, mark a finding important or dismiss it, and those decisions shape the next round.

Or let it run several rounds for you: the AI researcher. Set a number of rounds (1 to 20) and start from either the analytic you selected or a plain-English question. Each round runs an analytic on the chosen population and active cohort, asks the model for an insight on the result, asks for suggested next analytics, writes a short summary, and runs the top suggestion as the next round. You can stop after any step, continue from where it ended, and optionally pause to review and edit any AI-written query before it runs. It can only choose catalog analytics or plain-English questions, so the same limits apply as for the assistant, but it does chain steps without a click from you, so check the log before trusting the trail it followed.

You can look at the data itself, not only at results. The Patient data explorer lists the patients of the current scope and opens any one of them with their conditions, medications, lab series, procedures, encounters, allergies and raw FHIR resource. The Cohort knowledge graph is built from the active cohort: conditions, drugs, labs and procedures as nodes, and links where they occur in the same patients, with lift, which one usually comes first and the typical gap in days. Links that terminology.js already knows (for example a condition and its usual drug) are tagged, including known links that never appear in this cohort. These are co-occurrence counts, not clinical claims.

Text with no code can be coded, with a person in the loop. Some records carry only text, such as a diagnosis written "sugar diabetes" with no code. Code-based methods cannot see them. Code enrichment lets the model propose a code for each distinct string, you approve, edit or reject it, and the enriched methods (V3 and V5) then count the approved codes. Details are in the Code enrichment section below.

It is kept on a short leash by design. The model can only choose from the analytics catalog and the settings each analytic offers, or, for enrichment, from real candidate codes found in reference tables. It never runs SQL and never touches the database. The one place it writes a query is the custom analytic: it drafts a single read-only SELECT, you review and can edit it, and only then does it run as fixed SQL. That query runs on the plain scoped views, so it is offered for V1, V2 and V4 only. Every figure comes from a deterministic analytic or a query you approved, not from the model.

How a research session works

  1. Bring data and check it. Import your own FHIR files, fetch a sample from the HAPI test server, or generate a synthetic batch. Then run Analytics readiness to see how much of the data is coded, dated and narrative, and which analytics can run in which method.
  2. Ask, get ideas, or define. Type a question in plain English and the assistant fills in the PICO or PECO study form for you to review. Not sure what to ask? Press Suggest a few studies (optionally after typing a topic such as kidney or blood pressure) and pick one of up to four suggested questions, each checked against the known conditions, drugs and outcomes before it is shown. Or build a cohort yourself, including with the SNOMED CT query builder. A cohort is saved against one population (a batch or a batch group) and always runs on it.
  3. Run an analytic. Pick one from the catalog and a method (V1 to V5), or run the dashboard to cover everything for the cohort. For V3 and V5, tick which domains to enrich (conditions by default).
  4. Get a read. Ask for insights on one run or all runs, or press the suggestion button for flagged findings and proposed next steps. Results can also be explained in plain words.
  5. Steer. Run, skip, mark important or dismiss. Each step builds on your earlier decisions. Or start the AI researcher to chain a few rounds automatically and read the log afterwards.
  6. Fill coding gaps. Where records have text but no code, review proposed codes in the Enrichment panel, then use Compare V2 / V3 or Compare V4 / V5 to see what approved enrichment changed.
  7. Go deeper. Browse individual patients and the cohort knowledge graph.

The assistant works with your own OpenRouter key and a model you choose. It is optional: every analytic, cohort tool and export works without it.

Code enrichment (V3 and V5)

Enrichment adds codes to records that have a name but no source code. It is done once per distinct string, not per record, and a decision applies to every batch. It works for conditions, medications, labs, procedures, allergies and immunizations, and you choose which of them a run uses.

  1. Coverage. See the distinct uncoded strings of a domain, sorted by how many records carry them, and the share of records coded by source, coded by approved enrichment, and still uncoded.
  2. Candidates. For each string the app looks up real codes in the reference tables (the bundled dictionary and the SNOMED CT tables). A string with no candidate is marked unverified.
  3. Proposals. The model you configured may only pick one of those candidates, with a confidence, an assertion (confirmed, suspected or negated) and a short reason. A pick outside the candidate list is ignored. Only the strings and candidate codes are sent, never patient data, ids or dates.
  4. Review. You approve, edit (with a code search) or reject each proposal. Bulk approve approves confirmed proposals at or above a confidence you set; suspected and negated ones always need a person.
  5. Use and compare. V3 and V5 count approved and edited, confirmed codes. Results carry a banner showing how much of each domain was coded by enrichment and how many uncoded strings nobody has reviewed. The comparison buttons show the difference against V2 or V4.
  6. Check the AI. The Reviewer vs AI agreement report shows, for strings you decided one by one, how often you kept the model's code, split by the model's confidence, with the disagreements listed.

The rules are simple. Source codes always win over enriched ones. Enrichment adds codes, never dates, so V5 only helps records that already have a date. Proposed, rejected, suspected and negated rows count nowhere. V2 and V4 never read enrichment. Every review is written to the audit log.

Use cases

  • Explore an unfamiliar dataset with a guide. Run a first analytic, ask the assistant what stands out, and follow its suggestions, skipping what is not useful.
  • Let it explore a cohort for a few rounds. Start the AI researcher from an analytic or a plain-English question, set three to five rounds, then read the insight, suggestions and summary of each round to see where it went and why.
  • Turn a question into a study. Write the question in plain English, or ask for a few suggested studies on a topic, review the PICO or PECO form it fills in, run it, and have the result explained.
  • Assess a FHIR export before an ETL project. Run Analytics readiness and the data quality analytic and see coding coverage, unrecognised code systems and date problems.
  • See what a cohort looks like. Open the cohort knowledge graph to see which conditions, drugs and labs travel together, then open individual patients in the explorer to check a pattern against the record.
  • Try it on a public FHIR server. Fetch a few dozen patients from the HAPI test server and use Analytics readiness to see how much, or how little, their data supports. Test data only, never real patients.
  • Try enrichment on data with missing codes. Generate a batch with codes set to partly uncoded for a real-world mix of coded and text-only records, or fully uncoded to start from zero, then open the Enrichment panel and code the strings.
  • Measure what coding gaps cost. Review the proposed codes for conditions, then compare V2 with V3 to see how many more patients an analytic finds once text-only records are coded, and use the agreement report to judge how far to trust the model.
  • Compare phenotype definitions. Build a diabetes cohort by exact code, by code plus descendants, and by text, then compare how many patients each captures.
  • Explore care gaps and safety signals. Overdue screening, risky drug pairs, and prescribing after an allergy was recorded, on synthetic data you can share freely.
  • Teach clinical analytics. Generate a batch, assign students different cohorts, and have them explain why the text, code and time methods disagree.
  • Stress-test analytics code. Generate messy data with other code systems, local codes, mixed units and duplicates, and see what breaks.

When not to use it

  • Clinical decision-making or anything regulated. It is not a medical device, and the assistant gives no treatment advice.
  • Treating the assistant's output as findings, or enrichment as validated coding. Approved codes are a reviewed convenience for exploration, and the reviewer may be the only check.
  • Treating the assistant's output as findings. Its flags and suggestions, and the path the AI researcher follows across rounds, are AI-generated leads to check against the underlying tables. Results are descriptive and unadjusted.
  • Real patient data without your organization's approval. The app has sign-in, an audit log and a SELECT-only database role, but it has one role (admin), no federation and no regulatory certification, and it is not a validated clinical system. The assistant sends result tables, with patient-id columns removed and large tables cut, to a third-party model provider, so use it only if sending de-identified aggregates fits your policy. Enrichment sends only distinct strings and candidate codes, but a record's own text can still be sensitive, so apply the same policy.
  • Multi-site studies, formal phenotype validation or publication-grade inference. Counts are descriptive, the bundled terminology is demo content, and there is no peer-reviewed validation of the methods.
  • Very large datasets. Import is chunked and bulk-loaded, but it is still a single PostgreSQL instance, some analytics take minutes at thousands of patients, and the knowledge graph shows only the top concepts per type.

Scope and intent

Vibe Rounds is a research and teaching workbench with an AI assistant on top. It loads FHIR R4 data into PostgreSQL, lets you define cohorts, and runs a catalog of clinical analytics in five methods that differ in what evidence they use: narrative text (V1), source codes (V2), source codes plus approved enrichment codes (V3), codes plus time (V4), and enriched codes plus time (V5). Enrichment gives codes to text that has none: a model may only choose among real candidate codes from reference tables, a person approves, edits or rejects every proposal, and only approved codes count. Source codes always win, and enrichment adds codes, never dates. The assistant helps you read the results and decide what to ask next. Its central question is practical: how much do results change depending on whether you read the notes, trust the codes, fill the coding gaps, or reason over dates?

It is not a medical device, a clinical decision support system, or a certified terminology service. It is not an OMOP CDM implementation and does not transform data into one. Outputs are descriptive counts and associations for exploration, method comparison and education, and the human analyst stays in charge of every step.
