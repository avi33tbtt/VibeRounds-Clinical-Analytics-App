Architecture

How data moves from FHIR sources into a standardized database and on to analytics.

This is the complete architecture for your healthcare data analytics system.

Goal

Get FHIR healthcare data (JSON, NDJSON, CSV, etc.) → process it into a standardized database → run Python healthcare analytics on it.

System Architecture

Three Layers (with openEHR enhancement option)

  • Layer 1 - Data Ingestion (Web App): User selects folder → detects format → parses & validates → normalizes → loads into storage layer with a batch ID.
  • Layer 2 - Storage Layer (Option A - Direct FHIR or Option B - openEHR CDR):
    • Option A (Current Approach): Standardized PostgreSQL schema (Patient, Encounter, Observation, Diagnosis, Procedure, Medication, Allergy tables).
    • Option B (openEHR Enhancement): openEHR Clinical Data Repository (CDR) storing data via Reference Model + Archetypes, providing clinically validated, version-stable persistence with built-in governance.
  • Layer 3 - Analytics:
    • In-App Analytics (Node.js): Quick, preset analytics running directly in the web application. Provides immediate insights with predefined queries for prevalence, demographics, vital signs trends, and basic cohort analysis. Ideal for rapid prototyping and quick stakeholder reviews.
    • Python/Jupyter Analytics: Advanced, flexible analytics using the full Python ecosystem (pandas, scikit-learn, lifelines, spaCy, etc.). Enables custom modeling, survival analysis, NLP on clinical text, network analysis, and any research-grade investigation. Data is queried from PostgreSQL and processed locally.

Why Consider openEHR in the Architecture?

While FHIR-optimized tables work well for analytics, adding openEHR provides additional benefits for long-term clinical data management:

  • Clinical Data Modeling: Archetype-based, constraint-driven models (e.g., blood pressure observation) that are formally versioned and clinically governed.
  • Schema Stability: Adding new clinical concepts doesn't require SQL migrations - you simply publish new archetypes.
  • Separation of Concerns: Static Reference Model (information structure) + pluggable Archetypes (clinical meaning) governed by clinical safety processes.
  • Query Flexibility: AQL (Archetype Query Language) enables intuitive clinical queries like:
SELECT o/data[at0001]/value/magnitude FROM OBSERVATION o WHERE o/archetype_id = 'openEHR-OBSERVATION-blood_pressure-v1'
  • FHIR Compatibility: openEHR maps cleanly to FHIR - you can store the canonical clinical data in openEHR, then expose it as FHIR resources when needed for external systems or research consortia.
  • Tooling & Ecosystem: Mature open-source implementations (Ehrbase, NTDSC), GUI archetype designers, and clinical knowledge repositories.

Standardized Schema (FHIR-derived tables)

  • fhir_patient - demographics (patient_id, gender, birth_date, address)
  • fhir_encounter - encounters (patient_id, encounter_type, start_date, end_date)
  • fhir_observation - labs & vitals (patient_id, code, value, unit, effective_date)
  • fhir_diagnosis - conditions (patient_id, code, code_system, onset_date)
  • fhir_procedure - procedures (patient_id, code, performed_date)
  • fhir_medication - medications (patient_id, medication_code, prescribed_date)
  • fhir_allergy - allergies (patient_id, substance, reaction, severity)

Every table also stores: fhir_resource_type, fhir_resource_id, json_content (full original JSON), imported_at, ingestion_batch_id.

Preprocessing Pipeline (Format-Agnostic)

  1. Format Detection - auto-detect JSON / NDJSON / CSV / XML / HL7
  2. Parsing - convert to Python objects (FHIR resources)
  3. Validation - required fields, valid code systems (ICD-10, LOINC, SNOMED CT), valid dates
  4. Normalization - map columns → standard columns, standardize units, unify codes, handle missing values
  5. Deduplication - remove duplicate records
  6. Loading - batch inserts into PostgreSQL with batch_id tracking
  7. Data Quality Report - summary of records, errors, warnings, missing fields

The Key Guarantee

Once preprocessing completes successfully, the analytics layer is blind to the input format. It only sees the standard schema:

# This query is ALWAYS identical, regardless of input format (JSON, CSV, NDJSON) df = pd.read_sql_query(""" SELECT AVG(value) FROM fhir_observation WHERE code = '8480-6' -- LOINC: systolic blood pressure """, engine)

4 Methods of Analytics

Once your data is in the standardized schema, analytics can be run in 4 different ways. Here's how they compare:

Method What It Analyzes Standardization Complexity Best For
V1 Raw clinical text/notes (without coding) None — keyword search in free text (no coding) Low Quick exploration, keyword discovery
V2 Raw values (symptoms, comorbidities, meds) Full — LLM suggests codes, humans verify (SNOMED CT, RxNorm, LOINC, ICD-10) High (preprocessing) Building a high-quality coded dataset
V3 Pre-coded data in standardized tables Already coded — query SNOMED/RxNorm/LOINC/ICD-10 IDs Medium Standard analytics, quality measures, research
V4 Coded data + timestamps (effective_date) Coded + time-aware analysis High Longitudinal studies, progression, outcomes

Recommended Workflow

Start with V2 during ingestion (LLM + human coding of key clinical values) → this builds a high-quality coded dataset. Then:

  1. V3 for standard analytics (prevalence, demographics, comorbidities)
  2. V4 for longitudinal insights (progression, outcomes, adherence)
  3. V1 as a supplement for unstructured notes where coding wasn't feasible

Your data preprocessing step is the key decision point here — V2 in preprocessing means your entire analytics pipeline (V3/V4) runs on clean, standardized codes.

Instructions: from here to results in five steps
  1. Choose what to analyse below: population / batch, cohort, and which recipes to include. To use a SNOMED CT query, build it in Analytics > Create Custom Cohort > Build SNOMED CT Query and press Use in Python; it arrives here ready.
  2. Download notebook (.ipynb), or Preview cells to copy individual cells into your own notebook or script.
  3. Install the packages once: pip install pandas sqlalchemy psycopg2-binary matplotlib jupyterlab. For the recipes also: pip install lifelines scikit-learn networkx.
  4. Set the database password in your terminal, then start Jupyter in the folder with the notebook:
    macOS / Linux: export DB_PASSWORD=your-password then jupyter lab
    Windows PowerShell: $env:DB_PASSWORD="your-password" then jupyter lab
    If you skip this, the notebook asks for the password when it connects. Host, port, database and user default to this app's settings; override with DB_HOST, DB_PORT, DB_NAME, DB_USER.
  5. Open the notebook and choose Run > Run All Cells. The first cells connect and load the data, the orientation section shows what is in it, the recipes are independent: run, edit the parameters at the top of the cell, run again.

Changing cohort later: edit CRITERIA_SQL in the Scope cell (a SQL WHERE clause on fhir_patient, for example the cohort criteria from the SNOMED builder) and re-run from that cell down. Or generate a new notebook here.

If something goes wrong:

  • Connection refused / timeout: Jupyter must reach the database host and port. Run it on the same machine as the app, or set DB_HOST / DB_PORT.
  • password authentication failed: wrong DB_PASSWORD or DB_USER.
  • relation "fhir_patient_..." does not exist: the batch was deleted or renamed after the notebook was made. Generate it again.
  • ModuleNotFoundError: install the missing package with pip in the same Python that runs Jupyter.
  • Empty DataFrames: the cohort matches nobody in that population. Clear CRITERIA_SQL to test.
  • Recipe says "too few": it needs more data (events or discharges). Generate a larger synthetic batch with the inpatient and readmission options, or use real data.

Privacy: notebooks read patient-level data and saved outputs can contain it. The notebook opens a read-only session and never stores your password, but do not share it or commit it with outputs (use Kernel > Restart & Clear Outputs). Why it exists

Hospitals and health systems now hold large amounts of patient data in FHIR, but getting a trustworthy answer from it is still slow, specialist work. Four problems come up again and again:

The problemWhat Vibe Rounds gives you
The answer depends on how you read the record. Ask "how many patients have diabetes?" of the notes, of the codes, or of the codes with dates, and you often get three different numbers. Most tools show you one, without saying so.Three answers side by side. Every analytic runs from the clinical notes, the codes, and the codes with dates on the same patients, so you can see how much a result depends on the method and where the data is weak.
You do not know if the data is any good. Missing codes, local code systems, duplicates and impossible dates only surface after weeks of work, if at all.A data check up front. Coding coverage, unrecognised code systems and date problems are measured first, so you know what the data can support before you build on it. Analytics readiness goes one step further: it runs every analytic in each method once and tells you which ones this data can support, and why not for the rest.
Turning a clinical question into a study takes skill and time. You need to know the code sets, write cohort SQL, pick an analysis and decide what to look at next.A faster path from question to result. Type the question in plain English or ask for suggested studies, and the form is filled in for you. A query builder writes the cohort SQL from clinical concepts, including descendants in the SNOMED CT hierarchy.
General AI chat tools can invent numbers. A model that writes its own queries and quotes its own figures is hard to trust or to check in a clinical setting.An assistant that guides but does not calculate. The model reads results, flags what stands out, and proposes the next analysis from a fixed catalog. Every number comes from a tested analytic, nothing runs until you click, and you decide each step.

The value, in short: you get to a defensible first answer sooner, you know how much the method and the data quality matter, and you leave with something reusable, either the SQL or a notebook, instead of a one-off number. It does this on synthetic or de-identified data, with no need to convert your data to another model first.

What it does

You bring FHIR patient data, from your own files, the open HAPI FHIR test server or a built-in synthetic generator, and work through it in PostgreSQL: define a cohort, run a catalog of clinical analytics (prevalence, medication use, lab control, readmissions, care gaps, drug safety, data quality and more), and let the AI assistant read the results with you.

The assistant is analyst-led. After each run it reads every result so far, together with the choices you have already made. It summarizes where the analysis stands, flags what it noticed (important, unusual, caution, data quality), and proposes up to four next analytics with a short reason each. You run a suggestion, skip it, mark a finding important or dismiss it, and those decisions shape the next round.

You can look at the data itself, not only at results. The Patient data explorer lists the patients of the current scope and opens any one of them with their conditions, medications, lab series, procedures, encounters, allergies and raw FHIR resource. The Cohort knowledge graph is built from the active cohort: conditions, drugs, labs and procedures as nodes, and links where they occur in the same patients, with lift, which one usually comes first and the typical gap in days. Links that terminology.js already knows (for example a condition and its usual drug) are tagged, including known links that never appear in this cohort. These are co-occurrence counts, not clinical claims.

It is kept on a short leash by design. The model can only choose from the analytics catalog and the settings each analytic offers. It never writes SQL, never touches the database, and every figure comes from a deterministic analytic, not from the model.

How a research session works

  1. Bring data and check it. Import your own FHIR files, fetch a sample from the HAPI test server, or generate a synthetic batch. Then run Analytics readiness to see how much of the data is coded, dated and narrative, and which analytics can run in which method.
  2. Ask, get ideas, or define. Type a question in plain English and the assistant fills in the PICO or PECO study form for you to review. Not sure what to ask? Press Suggest a few studies (optionally after typing a topic such as kidney or blood pressure) and pick one of up to four suggested questions, each checked against the known conditions, drugs and outcomes before it is shown. Or build a cohort yourself, including with the SNOMED CT query builder.
  3. Run an analytic. Pick one from the catalog, or run the dashboard to cover everything for the cohort.
  4. Get a read. Ask for insights on one run or all runs, or press the suggestion button for flagged findings and proposed next steps. Results can also be explained in plain words.
  5. Steer. Run, skip, mark important or dismiss. Each step builds on your earlier decisions.
  6. Go deeper. Browse individual patients and the cohort knowledge graph, or export a Jupyter notebook for survival analysis, modelling or anything the interface does not offer.

The assistant works with your own OpenRouter key and a model you choose. It is optional: every analytic, cohort tool and export works without it.

Use cases

  • Explore an unfamiliar dataset with a guide. Run a first analytic, ask the assistant what stands out, and follow its suggestions, skipping what is not useful.
  • Turn a question into a study. Write the question in plain English, or ask for a few suggested studies on a topic, review the PICO or PECO form it fills in, run it, and have the result explained.
  • Assess a FHIR export before an ETL project. Run Analytics readiness and the data quality analytic and see coding coverage, unrecognised code systems and date problems.
  • See what a cohort looks like. Open the cohort knowledge graph to see which conditions, drugs and labs travel together, then open individual patients in the explorer to check a pattern against the record.

When not to use it

  • Clinical decision-making or anything regulated. It is not a medical device, and the assistant gives no treatment advice.
  • Treating the assistant's output as findings. Its flags and suggestions are AI-generated leads to check against the underlying tables. Results are descriptive and unadjusted.
  • Real patient data without authentication and your organization's approval. The app has no login and runs cohort SQL as written. The assistant sends result tables, with patient-id columns removed and large tables cut, to a third-party model provider, so use it only if sending de-identified aggregates fits your policy.
  • Multi-site studies, formal phenotype validation or publication-grade inference. Counts are descriptive, the bundled terminology is demo content, and there is no peer-reviewed validation of the methods.
  • Very large datasets. Import is chunked and bulk-loaded, but it is still a single PostgreSQL instance, some analytics take minutes at thousands of patients, and the knowledge graph shows only the top concepts per type.

Scope and intent

Vibe Rounds is a research and teaching workbench with an AI assistant on top. It loads FHIR R4 data into PostgreSQL, lets you define cohorts, and runs a catalog of clinical analytics in three ways that differ in what evidence they use: narrative text, codes, or codes plus time. The assistant helps you read the results and decide what to ask next. Its central question is practical: how much do results change depending on whether you read the notes, trust the codes, or reason over dates?

It is not a medical device, a clinical decision support system, or a certified terminology service. It is not an OMOP CDM implementation and does not transform data into one.
